# Baga AI — поиск и оценка аренды квартир (krisha.kz)

Файл написан для внешнего ревью. Он описывает цель, данные, архитектуру, принятые
решения с обоснованием и — отдельным разделом — то, что ещё **не** проверено.
Если вы ИИ-ревьюер: в конце есть список вопросов, по которым нужна критика.

Дата: 2026-09-22. Проект — финальный на курсе nFactorial, срок ~2 недели, команда 2 человека.
Обязательные требования курса: в проекте должны быть RAG и MCP.

---

## 1. Цель

Человек ищет квартиру в аренду и не понимает двух вещей: **где найти нужный ремонт**
и **не переплачивает ли он**. Продукт отвечает на оба вопроса.

```
запрос: «двушка в Алматы до 400к, светлая кухня в скандинавском стиле»
ответ:  10 объявлений + по каждому вердикт «цена ниже / в рынке / выше похожих»
```

Две подсистемы:

1. **Поиск по смыслу.** Стиль ремонта ищется по фотографиям и описаниям, жёсткие
   условия (цена, комнаты, район) — обычными фильтрами.
2. **Оценка справедливой цены.** Модель по характеристикам предсказывает диапазон
   месячной аренды; цена объявления сравнивается с этим диапазоном.

Ограничение, которое нельзя забывать: модель учится на **ценах в объявлениях**, а не
на ценах сделок. Она отвечает «дорого относительно похожих предложений», а не
«дорого объективно». Если рынок завышает целиком, модель этого не увидит.

Особенности, которые влияют на код:

- Пути к фото в базе **виндовые абсолютные** (`C:\Users\...\photos\<id>\<n>.jpg`) — берём хвост `<id>/<n>.jpg`.
- 191 фото физически лежит в папке **другого** объявления (следствие sha256-дедупа).

- Города и районы в базе латиницей (`almaty`, `Bostandykskiy_r-n`) — нормализуем в русские названия,
  иначе запросы пользователя не совпадут с данными.
- `duplicate_group_id`: 7 287 групп на 7 485 объявлений (одна квартира от нескольких риелторов).

## 3. Архитектура

### Офлайн (считается один раз)

```
krisha.db ─┐
           ├─→ Kaggle GPU: SigLIP 2 ──→ photo_emb.npy (72 963 × 768, float16, ~112 МБ)
photos/ ───┘                        ├─→ photo_rooms.parquet (тип комнаты, «рендер или фото»)
                                    └─→ listings_raw.parquet
                                              │
                            prepare ──→ listings.parquet (чистка, единая схема)
                            embed-text ──→ desc_emb.npy (описания, ALEM text-1024)
```

### Онлайн (на каждый запрос)

```
запрос → LLM разбирает на (жёсткие условия) + (стиль)
              ↓                        ↓
     фильтр по характеристикам    SigLIP по фото ─┐
     (цена, комнаты, район)       ALEM по описаниям ┴→ RRF → топ-10
              └──── ограничивает кандидатов ──────────┘
                                                        ↓
                                        модель цены → вердикт по каждому
```

## 4. Ключевые решения и обоснование

**SigLIP 2, а не DINOv3 и не open_clip.**
Основной сценарий — текстовый запрос. У DINOv3 нет текстового энкодера в принципе
(self-supervised на одних картинках), поэтому размер модели не помогает. У друга в Qdrant
уже лежат эмбеддинги open_clip ViT-B-32 (OpenAI), но она англоязычная и русские запросы
понимает плохо. SigLIP 2 мультиязычная и кладёт текст и картинки в одно пространство.
DINOv3 планируется отдельно: как признак «качество ремонта» (linear probing по
`renovation_text`) и для поиска дублей — там он объективно сильнее.

**Препроцессинг перенесён из прошлого проекта участника** (Kaggle «Lost in the Museum»,
DINOv3, 0.899): `resize_and_pad` (интерьер 4:3 не сплющивается), CLAHE как опция,
объединение видов `l2 → mean → l2`. Мультискейл 336/512 **не** перенесён: SigLIP обучена
на фиксированном разрешении, вне его качество падает (у DINOv3 это работало).

**Жёсткие условия не идут в вектор.** «До 400 000 ₸» и «не первый этаж» эмбеддингом
невыразимы, «скандинавский стиль» невыразим фильтром. Поэтому LLM разбирает запрос на две
части: `pydantic`-схема `Filters` + свободный текст стиля.

**Два канала ранжирования сливаются через RRF (k=60), а не по сырым скорам.**
Косинусы SigLIP и текстовой модели несравнимы по шкале, ранги сравнимы.

**Векторы в numpy, а не в векторной БД.** 72 963 × 768 float16 = 112 МБ, брутфорс-умножение
на вектор запроса — десятки миллисекунд. Qdrant на таком объёме добавил бы инфраструктуру
без выигрыша. Хранилище спрятано за один класс, замена на Qdrant — правка одного файла.

**Ярлыки комнат необязательны.** Нужны в основном для поиска по картинке (сгенерированная
гостиная иначе находит кухню в тех же тонах) и чтобы отсечь фасады, планировки и рендеры
застройщиков. Но жёсткий фильтр по неточному классификатору режет и правильные ответы,
поэтому по умолчанию он выключен для текстовых запросов, а без файла с ярлыками поиск
просто работает без фильтрации.

**Индекс фото хранит относительные пути** (`<listing_id>/<n>.jpg`): артефакты считаются на
Kaggle, а используются локально. Целостность связки «вектор ↔ фото» защищена хэшем списка
путей в `photo_emb.json` — при рассинхроне код падает, а не ищет по чужим векторам.

**Модель цены: квантильная регрессия (10/50/90) на `log(price)`.**
Пользователю нужен диапазон («похожие сдают за 380–470»), а не одно число. Логарифм —
из-за длинного правого хвоста цен и чтобы ошибка была относительной.
Бейзлайн для сравнения: медиана ₸/м² по району × площадь. Если CatBoost его не обгоняет,
проблема в признаках.

**Разбиение стратифицированное по районам и групповое по дублям** (`StratifiedGroupKFold`).
Район — главный фактор цены, он должен быть представлен в обеих частях. Дубли одной
квартиры не должны попадать и в train, и в test — иначе метрика завышена.
Для вердикта по **всем** объявлениям используются out-of-fold предсказания: каждая строка
предсказана моделью, которая её не видела.

## 5а. Дубли объявлений

Одна квартира часто висит на krisha несколько раз — от разных агентов, с теми же
фотографиями и разной ценой. Это портит три вещи сразу: выдача забивается повторами,
модель цены учится на одной квартире по нескольку раз, а покупатель не видит, что
объявление перевыставлено.

Как ищем (`notebooks/kaggle_dedup.ipynb`):

1. **DINOv3 ViT-L** считает эмбеддинг каждой фотографии. Для поиска стиля берётся SigLIP —
   он умеет сопоставлять текст и картинку. Здесь задача другая: найти **тот же самый**
   кадр, а не похожий по смыслу, и на instance retrieval DINOv3 сильнее.
2. Косинус с заниженным порогом 0.88 даёт кандидатов.
3. **SIFT + RANSAC** проверяет каждого кандидата геометрически: сколько точек ложится
   на одно преобразование. Настоящий дубль даёт сотни совпавших точек, похожая по
   стилю кухня — единицы.

Порог сборки групп подобран по данным и вынесен в `dedup.py`:

| Порог по inliers | Объявлений в группах | Максимальная группа |
|---|---|---|
| 18 (без отсечки) | 1 171 | **210** — цепочка, а не дубли |
| **40** | **611** | **6** |
| 200 | 510 | 6 |

При слабом пороге объявления с типовым ремонтом от застройщика сцепляются по цепочке
в одну гигантскую компоненту. От 40 до 200 результат практически не меняется — значит
настоящие дубли лежат сильно выше отсечки, а шум сильно ниже. Взяли 40 и добавили
защиту: если группа выросла больше 20 объявлений, сборка падает с ошибкой.

В карточке это видно как «ещё N объявлений с этими фото».

## 6. Что измерено, а что нет

**Измерено:** качество чистки данных, покрытие полей, корректность сопоставления фото и
объявлений, отсутствие утечек в разбиении.

**Модель цены измерена** (out-of-fold, 5 фолдов, стратификация по районам, группировка по дублям):

| Вариант | MAE, ₸ | MAPE, % | Покрытие 10–90 | Ширина интервала |
|---|---|---|---|---|
| бейзлайн: медиана ₸/м² по району × комнатам × площадь | 107 952 | 22.3 | 79.3% | 69% |
| CatBoost, базовые признаки | 86 898 | 17.0 | 66.3% | 38% |
| + ремонт (`renovation_text`, есть у 36%) | 85 674 | 16.6 | 66.5% | 38% |
| + признаки из описания (мебель, техника, депозит, санузел…) | 85 066 | 16.4 | 65.2% | 36% |
| **+ конформная калибровка (CQR)** | **85 066** | **16.4** | **81.1%** | **52%** |

Итог: ML обгоняет рыночный бейзлайн и по точности (22.3% → 16.4% MAPE), и по ширине
интервала (69% → 52%) при том же покрытии. Голая квантильная регрессия давала покрытие
66% вместо 80% — интервал был слишком узким, и система метила бы обычные квартиры как
завышенные; это чинится конформной калибровкой, а не переобучением модели.
Ступеньки «+ремонт» и «+текст» дали мало (17.0 → 16.4), то есть основную работу делают
площадь, комнаты, этаж и локация.

По сегментам: Алматы MAPE 16.1% / покрытие 81%, Каскелен 22.7% / 79% (264 объявления).
Худший сегмент — дорогие квартиры: MAPE 21.8%, покрытие 74%.

Утечка, которую пришлось закрыть: у 60% объявлений цена написана прямо в описании
(«… 750 000 ₸ за месяц …»), у 57.6% — ровно целевое значение. `features.clean_description`
маскирует любое число от 10 000, а `assert_no_price_leak` роняет обучение, если цена
всё же осталась в тексте.

**Не измерено вообще:** качество поиска (ни по тексту, ни по картинке), точность
zero-shot классификатора комнат, качество детектора рендеров.

Инструменты для измерения написаны заранее и ждут данных:

- `validate robust` — чувствительность векторов к качеству съёмки, освещению, ракурсу и
  «ИИ-глянцу»: реальные фото портятся известными искажениями, считается Hit@5 по каждому типу.
  Идея перенесена из museum-ноутбука участника.
- `validate review` / `score` — ручная разметка топ-5 по 30–50 запросам → precision@5,
  отдельно для текстовых и картиночных запросов.
- `validate rooms` — точность классификатора комнат по 200 размеченным вручную фото.
- Для модели цены: MAE/MAPE против бейзлайна + **покрытие интервала** (доля цен, попавших
  в коридор 10–90; должно быть ≈80%) и средняя ширина интервала.

## 7. Известные риски и ограничения

1. **Модель цены учится на ценах объявлений, а не сделок.** Системное завышение рынка невидимо.
2. **Один снимок данных.** Мониторинг во времени и разговор про дрейф невозможны, пока
   парсер не начнёт запускаться регулярно.
3. **`year_built` и `building_type` практически отсутствуют** — из модели цены выпадает
   существенный фактор. Достать их можно только повторным сбором детальных страниц.
4. **Сгенерированные ИИ картинки идеализированы**, реальные фото сняты на телефон, часто
   тёмные и широкоугольные. Насколько это сдвигает векторы — неизвестно до `validate robust`.
5. **Геозапросов нет** («рядом со школой»): координаты только у 41%, инфраструктура не подключена.
6. **Фильтр по типу комнаты теряет правильные ответы** на ошибках классификатора.
7. **Каскелен — 3.5% данных.** Модель будет заметно хуже там, чем в Алматы.
8. **Данные собраны скрапингом krisha.kz** для некоммерческого учебного проекта; датасет
   и фото не публикуются.

## 8. Структура кода

```
config.py        пути, модели, пороги (всё через env / .env)
listings.py      КОНТРАКТ ДАННЫХ: RENAME, чистка, нормализация, pydantic-схема Filters
photos.py        индекс фото (относительные пути), абсолютные — отдельной колонкой
embed.py         SigLIP 2: препроцессинг (pad/CLAHE), шарды с возобновлением, тексты
rooms.py         zero-shot: тип комнаты, «рендер или фото»
text_embed.py    эмбеддинги описаний (ALEM text-1024)
search.py        PhotoSearch (группировка по объявлению) + ListingSearch (фильтры + RRF)
splits.py        StratifiedGroupKFold: страты — район, группы — дубли
features.py      признаки: адрес -> район/мкр/улица, флаги из описания, ЗАЩИТА ОТ УТЕЧКИ ЦЕНЫ
price_model.py   бейзлайн, CatBoost MultiQuantile на log(price), CQR, метрики out-of-fold
validate.py      robust / review / score / rooms
mock_data.py     синтетика, чтобы каркас работал без реальных данных
run_pipeline.py  CLI: mock, prepare, status, index, embed, rooms, embed-text, search, validate
kaggle_embed.ipynb  векторизация на Kaggle GPU → артефакты в формате этого проекта
```

Запуск:

```bash
python run_pipeline.py prepare      # сырые объявления -> единая схема
python run_pipeline.py status       # что посчитано, какие каналы поиска включатся
python run_pipeline.py search --text "светлая кухня" --city алматы --rooms 2 --price-max 400000
```

## 9. Вопросы к ревьюеру

1. **Выбор моделей.** SigLIP 2 base для текст-картинка на русском, ALEM text-1024 для
   описаний, DINOv3 позже для «качества ремонта» и дублей. Что бы вы поменяли?
2. **Слияние каналов.** RRF с равными весами против взвешенной суммы нормированных скоров
   или обучаемого реранкера — при 7.5 тыс. объявлений и отсутствии разметки.
3. **Модель цены.** Достаточно ли признаков, учитывая, что год постройки и тип дома
   отсутствуют, а координаты есть у 41%? Стоит ли добавлять эмбеддинг описания как признаки
   (риск утечки: описание часто начинается с цены) и предсказание ремонта по фото?
4. **Интервал.** Квантильная регрессия против конформного предсказания на остатках —
