# Архитектура Baga AI

Авторы: Исламбек Султанбек и Нурдаулет.

Продукт отвечает на два вопроса арендатора: **где найти квартиру с нужным ремонтом** и
**не выше ли её цена, чем у похожих**.

## Общая схема

```
                         ОФЛАЙН (считается один раз)
  krisha.db ─┐
             ├─→ Kaggle GPU: SigLIP 2 ──→ векторы фото (72 963 × 768)
  photos/ ───┘                        ├─→ тип комнаты, «рендер или фото» (zero-shot)
                                      └─→ listings_raw.parquet
                                                │
                              prepare ──→ listings.parquet (чистка, единая схема)
                              embed-text ──→ векторы описаний (ALEM text-1024)
                                                │
                                          Qdrant: listing_photos_siglip
                                                  listing_descriptions

                         ОНЛАЙН (на каждый запрос)
  сайт (FastAPI) ───┐  вход, роль, лимит     голос ─► Gemini STT
  Telegram-бот ─────┼──────────────────────────────────┐
  MCP-клиент ───────┘                                  ▼
                              guardrails (инъекции, PII, домен)
                                                       ▼
  LangGraph: parse ─► confirm? ─► search ⇄ relax ─► answer
               │                    │                  │
     смысловой кэш ─► LLM      фильтры в Qdrant     LLM-ответ по найденному
     (подпись + косинус)       + фото (SigLIP 2)        │
                               + описания (ALEM)        ▼
                               → RRF (k=60)       guardrails на выходе
                               → CatBoost-вердикт  (суммы, id, формулировки)
                                                        ▼
                                                   текст ─► Gemini TTS

  Все LLM-вызовы: llm.py — Gemini 3.6 Flash ─► ALEM ─► шаблон без LLM
                  (предохранитель, дневной бюджет, кэш ответов)
  Все шаги: Langfuse — трейс на запрос, узлы графа, токены, цена, 👍/👎
```

### Путь одного запроса

«двушка в Бостандыке до 400 тысяч, светлая кухня» от пользователя до ответа:

1. **Вход.** `auth.py`: роль `user`, лимит 60 LLM-действий в час не исчерпан. Открывается
   трейс Langfuse с `user_id` и `session_id`.
2. **guardrails.check_input.** Инъекций нет, PII нет, город поддерживается.
3. **parse.** `semantic_cache` ищет запрос с той же подписью
   (`{n:[400000], w:[r2,kitchen,to], d:[бостан]}`) и косинусом ≥ 0.94. Промах →
   `llm.complete_json` → Gemini 3.6 Flash (thinking minimal, 1.4 с, $0.0007) →
   `rooms=[2], districts=[бостандык], price_max=400000, photo_rooms=[kitchen]`,
   стиль «светлая кухня». Результат кладётся в кэш.
4. **confirm?** Модель ничего не додумала → пауза не нужна.
5. **search.** Фильтры внутри Qdrant; SigLIP 2 кодирует «светлая кухня», поиск только по фото
   кухонь (≈50 мс); ALEM text-1024 — по описаниям; RRF; CatBoost даёт p10/p50/p90 и вердикт
   каждому из 6 результатов.
6. **answer.** Gemini пересказывает выдачу со ссылками на id (2.5 с, $0.0017).
   `guard_output` сверяет каждую сумму и id с фактами; выдумка → шаблон.
7. **Ответ.** Текст, карточки, «Почему цена?», 👍/👎 (пишется на тот же трейс).

Замер на 6 запросах (прогретый сервис, встроенный Qdrant): **медиана 6.2 с, максимум 8.1 с**,
≈ $0.0024 за запрос. Из них поиск ≈ 3 с (Qdrant 1–1.4 с во встроенном режиме, эмбеддинг
описания в ALEM 1.9 с), разбор 1.4–1.9 с, ответ 2.3–2.7 с. Повтор или перефразировка —
дешевле за счёт кэша.

## Решения и обоснования

**SigLIP 2 для фото.** Основной сценарий — текстовый запрос. У DINOv3 нет текстового
энкодера (обучалась только на картинках), у open_clip ViT-B-32 слабый русский.
SigLIP 2 мультиязычная и кладёт текст и картинки в одно пространство.

**Chunking: не применяется.** Единица индексации — объявление. Медиана описания
508 символов, это короче окна модели; резать нечего. Осознанное решение, а не упущение.

**Qdrant, а не матрица в памяти.** Фильтры по характеристикам выполняются внутри базы
вместе с векторным поиском, группировка по объявлению — запросом `query_points_groups`
(у квартиры 10–20 фото, иначе одна занимает весь топ). Два режима: встроенный (без
сервера) и сервер из docker-compose.

**Слияние каналов через RRF, а не по сырым скорам.** Косинусы SigLIP и текстовой модели
несравнимы по шкале, ранги сравнимы. Вес канала описаний — 0.5: при равных весах визуальный
судья видел нужное на фото лишь в 59.5% топ-5, при 0.5 — в 81.9% (EVALS.md, раздел 8).

**Реранкер: проверен и выключен.** Gemini, глядя на фото топ-12, по независимой метрике даёт
+1.7 п.п. (шум) при +4 с и ×4 цене запроса. Включается `RERANK=1`.

**Fine-tuning: LoRA на текстовую башню SigLIP 2 проверена и не включена** — +3.1 п.п. на
визуальном судье, меньше шума. Причина в данных: описания объявлений почти не описывают то,
что видно на фото (EVALS.md, раздел 9).

**Жёсткие условия не идут в вектор.** «До 400 000 ₸» эмбеддингом невыразимо,
«скандинавский стиль» невыразим фильтром. LLM разбирает запрос на две части.

**Модель цены: квантильная регрессия на `log(price)` + конформная калибровка.**
Пользователю нужен диапазон, а не фальшиво точное число. Логарифм — из-за длинного
правого хвоста цен. Калибровка нужна, потому что голая квантильная регрессия дала
покрытие 66% вместо 80%.

**Разбиение: страты по районам, группы по дублям.** Район — главный фактор цены.
Дубли одной квартиры не должны попадать и в train, и в test.

## Агент (LangGraph)

```
    parse ──► confirm? ──да──► [ПАУЗА: подтверждение пользователя] ──┐
      │                                                              │
      └──нет────────────────────────────────────────────────────────►├──► search
                                                                      │      │
                             ┌────────── relax ◄── пусто, попыток<3 ──┘      │
                             │            (ЦИКЛ)                             │
                             └────────────────────────────────────────► answer ──► END
```

| Узел | Что делает |
|---|---|
| `parse` | LLM разбирает запрос на жёсткие условия (`Filters`) и стилевую часть |
| `confirm` | пауза через `interrupt()`, если LLM домыслила условие, которого не было в запросе |
| `search` | фильтры в Qdrant + поиск по фото и описаниям + вердикт по цене |
| `relax` | ослабляет ОДНО условие и возвращает в `search` (цикл, до 3 попыток) |
| `answer` | генерация ответа по найденному со ссылками на id |

**Почему ветвление именно такое.** Подтверждение спрашивается не всегда, а только когда
модель добавила условие от себя: спрашивать каждый раз — раздражать, не спрашивать никогда —
молча резать выдачу. При отказе удаляются ровно те поля, которые модель домыслила
(`assumed_fields`), а не все подряд.

**Зачем цикл.** На запросе «трёшка в Каскелене до 60 тысяч» кандидатов ноль. Агент поднимает
цену на 30% (всё ещё ноль), убирает ограничение по комнатам (17 кандидатов) и отвечает,
честно перечислив, что именно ослабил. Без цикла пользователь видел бы пустой экран.

**Почему LangGraph, а не CrewAI/Parlant.** Нужен явный граф с условными переходами, циклом
и остановкой на человеке, а не команда автономных агентов: шаги здесь детерминированы,
«переговоры» между агентами задаче не нужны. `interrupt()` + чекпоинтер дают паузу
из коробки, в CrewAI это пришлось бы городить руками.

**Запасной режим.** Если LLM недоступна, `query_parser` откатывается на разбор регулярками
(числа, «двушка», город) — выдача хуже, но продукт работает.

## Интеграция: агент, MCP-сервер, сайт

Сайт, агент и MCP-сервер вызывают одни и те же функции `api.py` — поэтому ответ одинаковый,
через какой бы интерфейс ни пришёл вопрос. Функции возвращают JSON-совместимые словари:

| Функция | Что делает |
|---|---|
| `search_listings(query, city, districts, rooms, price_max, …)` | поиск по условиям и стилю, с вердиктом по цене у каждого результата |
| `estimate_price(listing_id \| listing)` | диапазон p10/p50/p90, вердикт, надёжность |
| `get_comparables(listing_id)` | похожие объявления, на которых построен вердикт |
| `get_listing(listing_id)` | карточка объявления |

Две детали, важные для корректного вердикта:

- для объявлений из базы отдаются **out-of-fold** предсказания (модель их не видела),
  для новых — обученная на всех данных модель; поле `source` показывает, что именно;
- при малом числе аналогов `reliable=false`, и это надо показывать пользователю,
  а не прятать за уверенной цифрой.

### MCP-сервер (`mcp_server.py`)

| Инструмент | Что делает |
|---|---|
| `search_apartments` | поиск по условиям и описанию ремонта; у каждого результата вердикт по цене и ссылка на фото |
| `check_rent_price` | p10/p50/p90 и вердикт — по id, **ссылке krisha.kz** или характеристикам квартиры не из базы |
| `get_comparables` | аналоги, на которых построен вердикт, и правило отбора (`matched_by`) |
| `get_listing` | карточка объявления |

**Почему MCP, а не обычный HTTP API.** Потребитель — LLM-клиент (Claude Desktop, Claude Code,
Cursor). Ему нужны не эндпоинты, а инструменты с описанием и схемой параметров, которые
модель сама выбирает по ходу разговора: человек присылает ссылку на krisha — модель зовёт
`check_rent_price`, спрашивает «на чём основан вывод» — `get_comparables`. MCP даёт это без
отдельной интеграции под каждое приложение.

**Почему эти 4 инструмента.** Они повторяют вопросы арендатора: «найди», «дорого ли»,
«докажи», «покажи». Внутренние шаги (разбор запроса, RRF, ослабление фильтров) наружу не
выставлены: это решения агента, а не операции, которые нужны клиенту.

Детали: все инструменты только читают (`readOnlyHint`); свободный текст стиля проходит
входной фильтр; stdout во время вызова перенаправлен в stderr — в stdio-режиме stdout это
канал протокола, и любой `print` при загрузке моделей сломал бы клиенту JSON-RPC.

```bash
python mcp_server.py --selftest                                   # MCP-клиент в памяти вызывает инструменты
claude mcp add baga-ai -- "$(which python)" "$PWD/mcp_server.py"  # подключить к Claude Code
```

## Guardrails (`guardrails.py`)

```
запрос ─► [ВХОД] инъекция? ──да──► разбор регулярками, в LLM не идёт ─┐
             │ PII → маска, другой город / покупка → предупреждение   │
             └──нет──► LLM-разбор ──────────────────────────────────────┴─► поиск ─► LLM-ответ
                                                                                        │
                            [ВЫХОД] суммы и id сверены с фактами, нет «переплачиваете», ◄┘
                                    нет чужих городов? ──нет──► шаблонный ответ из тех же фактов
```

**Своя реализация, а не Guardrails AI / NeMo.** Три LLM-вызова с узкими задачами, и для каждого
известно, что считать нарушением. Проверки детерминированные: регулярки на входе, сверка с
фактами на выходе. Не стоят токенов и латентности, ведут себя одинаково в evals и в проде.
Фреймворк добавил бы зависимость и, как правило, ещё один LLM-вызов на проверку.

**Инъекция не блокирует пользователя.** Такой запрос не отправляется в LLM, но разбирается
запасным путём на регулярках, и стилевая часть всё равно идёт в поиск по фото. Человек, у
которого в запросе случайно оказалось «забудь», получит выдачу, а модель — никаких команд.

Метрики фильтра и найденные им реальные сбои — `EVALS.md`, раздел 4.

## Слой LLM (`llm.py`)

Все генерации идут через `llm.complete()`, и в одном месте решено, что происходит, когда
модель недоступна или дорожает.

| Механизм | Как работает | Зачем |
|---|---|---|
| Цепочка провайдеров | `LLM_CHAIN=gemini,alem`: первый доступный отвечает | основная LLM упала — отвечает следующая |
| Повтор | одна повторная попытка на 408/429/499/5xx | короткие сбои не доходят до фолбэка |
| Таймаут по задаче | разбор 10 с, ответы 20 с; на таймаут — сразу фолбэк, без повтора | хвосты Gemini: на замере разбор 14.7 с, один вызов упал с 499 через 26 с — запрос шёл 23–33 с. После — максимум 8.1 с |
| Предохранитель | 3 ошибки подряд — провайдер выключен на 60 с | не ждать таймаут мёртвого сервиса на каждом запросе |
| Бюджет | дневной `LLM_DAILY_BUDGET_USD`; превышен — платные пропускаются | «резко подорожала» — переходим на бесплатный ALEM, сервис не падает |
| Последний рубеж | все упали — `LLMUnavailable`, ответ собирается шаблоном из фактов | вердикт по цене от LLM не зависит, только формулировка |
| Точный кэш | SQLite, ключ — промпт + параметры + модели; только при temperature 0 и только полные ответы | «Почему цена?» по одному объявлению считается один раз |
| Смысловой кэш | `semantic_cache.py` для разбора запроса | перефразировка не идёт в LLM |

**Почему свой шлюз, а не LiteLLM.** Провайдеров два, а главная особенность — thinking-токены
Gemini, съедающие `max_output_tokens`, — обёртками не решается. Своего кода — 300 строк
с тестами на каждый механизм (`tests/test_llm.py`).

**Смысловой кэш: почему нужна подпись.** «до 400 тысяч» и «до 500 тысяч» почти совпадают по
эмбеддингу, но фильтры у них разные. Поэтому попадание требует совпадения детерминированной
подписи (числа, комнаты, город, район, этажи, «от/до», комнаты на фото) И косинуса ≥ 0.94.
Порог подобран на парах «светлая / тёмная кухня» (косинус 0.938!) — см. EVALS.md, раздел 7.

## Пользователи и роли (`auth.py`)

| Роль | Что доступно | Почему |
|---|---|---|
| guest | поиск по описанию и фото, вердикт по цене, шаблонные объяснения | ноль LLM-вызовов: можно выставить в интернет без риска для бюджета |
| user | + ассистент, объяснения LLM, голос, отзывы; 60 LLM-действий в час | каждое действие стоит денег — лимит защищает бюджет от одного пользователя |
| admin | + админ-панель: расход и бюджет, провайдеры, кэш, отзывы, пользователи | эксплуатация без доступа к серверу |

Пароли — PBKDF2-SHA256 (200 000 итераций, соль на пользователя), стандартная библиотека.
Первый админ создаётся из `BAGA_ADMIN_USER` / `BAGA_ADMIN_PASSWORD`.

## Сайт (`server.py`, `web/`)

FastAPI отдаёт JSON API и статический фронтенд без сборки (HTML, CSS, ES-модули).
Сначала сайт был на Streamlit; от него отказались по двум причинам: главной странице нужны
вёрстка и анимация, которых Streamlit не даёт, а пауза ассистента на подтверждение — это
обычный запрос-ответ (`/api/assistant` → `paused` → `/api/assistant/resume`), а не
перезапуск всего скрипта на каждый клик.

| Страница | Что на ней |
|---|---|

Роли проверяются на сервере (`require("assistant")` и т. п.), фронтенд только прячет
недоступное. Эндпоинты синхронные — FastAPI выполняет их в пуле потоков, модели общие.
Голос из браузера (webm/mp4) перекодируется ffmpeg в WAV перед Gemini.

## Голос и Telegram

**Голос — каскад, а не нативная audio-to-audio модель.** Речь → Gemini STT → тот же
LangGraph-агент → текст → Gemini TTS. Нативная голосовая модель (Gemini Live) отвечала бы
сама — без поиска по базе, без подтверждения условий и без проверки цифр guardrails'ами.
Каскад дороже по латентности (+2.6 с STT, +4 с TTS), зато ответ тот же, что текстом.

**Telegram-бот** (`telegram_bot.py`): квартиры ищут с телефона, а ссылки на krisha пересылают
в мессенджере. Бот принимает текст, голосовые и ссылки `krisha.kz/a/show/<id>` (проверка
цены); пауза агента на подтверждение — inline-кнопки; 👍/👎 — оценка на трейс Langfuse.
Long polling, а не вебхук: не нужен публичный HTTPS, работает и с ноутбука, и из compose.

## Трейсинг (`tracing.py`)

**Langfuse — основной.** Один трейс на запрос пользователя: `assistant` (agent) →
узлы LangGraph (через `CallbackHandler`) → `parse_query` и `answer_search` (generation:
модель, параметры, токены, цена) → `search_listings` (retriever) → `estimate_price` (tool).
На трейсе — `user_id`, `session_id`, канал (web/telegram); 👍/👎 пишутся как score на тот же
трейс, поэтому плохой ответ открывается в один клик вместе с промптом.

Почему Langfuse: вызовы Gemini идут не через клиент OpenAI, и автоинструментация их не
видит — нужна ручная запись generation с ценой, в Langfuse это штатно; есть готовый
колбэк для LangGraph; сессии и оценки пользователей — из коробки.

**Phoenix — локальная опция** без аккаунта: `TRACING=1`, дашборд на :6006.

## Развёртывание

```bash
cp .env.example .env        # ключи Gemini / ALEM / Langfuse
docker compose up -d        # Qdrant + загрузка индекса + сайт: http://localhost:8501
docker compose --profile telegram up -d    # ещё и бот (TELEGRAM_BOT_TOKEN)
```

Образ: `python:3.12-slim`, torch для CPU (GPU сервису не нужен — кодируется только запрос,
~50 мс), веса SigLIP 2 скачиваются при сборке, пользователь без root, healthcheck.
`init` загружает векторы в Qdrant один раз (`qdrant_store.py ensure`), повторный запуск
ничего не пересобирает.

## Выбор моделей и параметров

| Задача | Что выбрали | Почему |
|---|---|---|
| Фото ↔ текст | `siglip2-base-patch16-224` | нужен общий вектор для картинок и текста; мультиязычная. Альтернатива `so400m-patch14-384` сильнее, но в 4–5 раз дольше (40–60 мин против 10 на Kaggle T4), а замеренное качество базовой версии нас устроило: precision@5 33–37% против 7.7% случайного выбора |
| Эмбеддинги описаний | ALEM `text-1024` | SigLIP плохо сравнивает текст с текстом; ALEM доступен по ключу курса, русский родной |
| LLM (разбор, объяснения, ответ) | **Gemini 3.6 Flash** (Vertex AI), фолбэк ALEM `alemllm` | выбрано A/B на 4 задачах (`ab_models.py`, EVALS.md раздел 6): разбор запроса 100% точных против 77.8% у ALEM и 0 выдуманных условий против 25% проваленных ловушек; объяснения — покрытие 85% против 65%; вдвое быстрее (p50 1.4–2.5 с против 2.7–5.8 с). Цена ≈ $0.0024 за запрос ассистента. ALEM бесплатный и остаётся фолбэком и судьёй |
| Судья в evals | ALEM `alemllm`, фолбэк Gemini | согласие с разметкой одинаковое (каппа 0.63 у обоих) — платить за судью незачем |
| Речь | STT Gemini 3.6 Flash, TTS `gemini-2.5-flash-lite-preview-tts` | STT распознал фразу с ценой и районом дословно за 2.6 с; Lite-TTS — 4 с против 6–16 с у старших TTS |
| Модель цены | CatBoost, `MultiQuantile` | категориальные признаки (район, улица, микрорайон) без ручного кодирования, устойчив к пропускам (у нас 41% координат, 36% ремонта), квантильная функция потерь из коробки |
| Не выбрали: DINOv3 | — | нет текстового энкодера, для текстового запроса непригодна. Оставлена как кандидат для признака «качество ремонта» по фото |

Параметры генерации подобраны экспериментами (`ab_generation.py` — раздел 3, `ab_models.py` — раздел 6 EVALS.md):

| Параметр | Значение | Почему |
|---|---|---|
| `temperature` | 0.0 | достоверность на 0 / 0.3 / 0.7 одинаковая (0 выдуманных сумм и id), 0 даёт воспроизводимость |
| `top_p` | 1.0 | при temperature 0 декодирование жадное, top_p нейтрален; при 0.7 сужение до 0.5 достоверность не меняет |
| `max_tokens` | 800 | при прежних 400 обрывалась **половина** ответов по выдаче (русский у alemllm ≈ 1.7 символа на токен); при 800 — ни одного |
| `thinking_level` (Gemini) | minimal | по умолчанию thinking включён и съедал лимит: 382 из 400 токенов ушли на рассуждения, ответ оборван. minimal — 100% точных разборов; low не лучше, но в 2.5–4 раза дороже; medium хуже (додумывает «центр» в районы). Шлюз добавляет к лимиту резерв под мысли, чтобы `max_tokens` значил длину ответа у обоих провайдеров |

Судья в evals и разбор запроса работают на `temperature=0` (нужна воспроизводимость).

## Ограничения

- Модель учится на ценах **объявлений**, а не сделок: отвечает «дороже похожих предложений».
- Один срез данных — динамики рынка и мониторинга дрейфа пока нет.
- Каскелен это 3.5% выборки, там ошибка заметно выше.
- Геозапросов («рядом со школой») нет: координаты только у 41%.
