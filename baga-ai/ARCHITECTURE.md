# Архитектура Baga AI

Продукт отвечает на два вопроса арендатора: **где найти квартиру с нужным ремонтом** и
**не выше ли её цена, чем у похожих**.

## Общая схема

```
                         ОФЛАЙН (считается один раз)
  krisha.db ─┐
             ├─→ Kaggle GPU: SigLIP 2 ──→ векторы фото (72 963 × 768)
  photos/ ───┘                        ├─→ тип комнаты, «рендер или фото» (zero-shot)
                                      └─→ listings_raw.parquet
                                                │
                              prepare ──→ listings.parquet (чистка, единая схема)
                              embed-text ──→ векторы описаний (ALEM text-1024)
                                                │
                                          Qdrant: listing_photos_siglip
                                                  listing_descriptions

                         ОНЛАЙН (на каждый запрос)
  запрос → LLM разбирает на (жёсткие условия) + (стиль)
                    ↓                               ↓
        фильтры внутри Qdrant                поиск по фото + по описаниям
        (город, комнаты, цена, площадь)              ↓
                    └──────────────→ RRF (k=60) → топ-10
                                                     ↓
                                    CatBoost: интервал цены → вердикт
                                                     ↓
                                    LLM-объяснение по аналогам (RAG)
```

## Компоненты

| Файл | Роль |
|---|---|
| `listings.py` | контракт данных: `RENAME`, чистка, нормализация, pydantic-схема `Filters` |
| `photos.py` | индекс фото (относительные пути), связка с объявлениями |
| `embed.py` | SigLIP 2: препроцессинг, шарды с возобновлением, текстовые запросы |
| `rooms.py` | zero-shot тип комнаты и детектор рендеров |
| `text_embed.py` | эмбеддинги описаний (ALEM text-1024) |
| `qdrant_store.py` | Qdrant: загрузка, фильтры в базе, группировка по объявлению |
| `search.py` | объединение каналов через RRF |
| `features.py` | признаки модели цены + защита от утечки цены из текста |
| `splits.py` | StratifiedGroupKFold: страты по районам, группы по дублям |
| `price_model.py` | бейзлайн, CatBoost квантили, конформная калибровка |
| `predict.py` | оценка одного объявления: интервал, вердикт, аналоги |
| `api.py` | **публичный слой для агента и MCP**: 4 функции, обычные словари |
| `validate.py` | проверки качества поиска |
| `notebooks/kaggle_embed.ipynb` | векторизация 71 679 фото на Kaggle GPU |
| `notebooks/price_model.ipynb` | модель цены по шагам, с прогоном |

## Решения и обоснования

**SigLIP 2 для фото.** Основной сценарий — текстовый запрос. У DINOv3 нет текстового
энкодера (обучалась только на картинках), у open_clip ViT-B-32 слабый русский.
SigLIP 2 мультиязычная и кладёт текст и картинки в одно пространство.

**Chunking: не применяется.** Единица индексации — объявление. Медиана описания
508 символов, это короче окна модели; резать нечего. Осознанное решение, а не упущение.

**Qdrant, а не матрица в памяти.** Фильтры по характеристикам выполняются внутри базы
вместе с векторным поиском, группировка по объявлению — запросом `query_points_groups`
(у квартиры 10–20 фото, иначе одна занимает весь топ). Два режима: встроенный (без
сервера) и сервер из docker-compose.

**Слияние каналов через RRF, а не по сырым скорам.** Косинусы SigLIP и текстовой модели
несравнимы по шкале, ранги сравнимы.

**Жёсткие условия не идут в вектор.** «До 400 000 ₸» эмбеддингом невыразимо,
«скандинавский стиль» невыразим фильтром. LLM разбирает запрос на две части.

**Модель цены: квантильная регрессия на `log(price)` + конформная калибровка.**
Пользователю нужен диапазон, а не фальшиво точное число. Логарифм — из-за длинного
правого хвоста цен. Калибровка нужна, потому что голая квантильная регрессия дала
покрытие 66% вместо 80%.

**Разбиение: страты по районам, группы по дублям.** Район — главный фактор цены.
Дубли одной квартиры не должны попадать и в train, и в test.

## Агент (LangGraph)

```
    parse ──► confirm? ──да──► [ПАУЗА: подтверждение пользователя] ──┐
      │                                                              │
      └──нет────────────────────────────────────────────────────────►├──► search
                                                                      │      │
                             ┌────────── relax ◄── пусто, попыток<3 ──┘      │
                             │            (ЦИКЛ)                             │
                             └────────────────────────────────────────► answer ──► END
```

| Узел | Что делает |
|---|---|
| `parse` | LLM разбирает запрос на жёсткие условия (`Filters`) и стилевую часть |
| `confirm` | пауза через `interrupt()`, если LLM домыслила условие, которого не было в запросе |
| `search` | фильтры в Qdrant + поиск по фото и описаниям + вердикт по цене |
| `relax` | ослабляет ОДНО условие и возвращает в `search` (цикл, до 3 попыток) |
| `answer` | генерация ответа по найденному со ссылками на id |

**Почему ветвление именно такое.** Подтверждение спрашивается не всегда, а только когда
модель добавила условие от себя: спрашивать каждый раз — раздражать, не спрашивать никогда —
молча резать выдачу. При отказе удаляются ровно те поля, которые модель домыслила
(`assumed_fields`), а не все подряд.

**Зачем цикл.** На запросе «трёшка в Каскелене до 60 тысяч» кандидатов ноль. Агент поднимает
цену на 30% (всё ещё ноль), убирает ограничение по комнатам (17 кандидатов) и отвечает,
честно перечислив, что именно ослабил. Без цикла пользователь видел бы пустой экран.

**Почему LangGraph, а не CrewAI/Parlant.** Нужен явный граф с условными переходами, циклом
и остановкой на человеке, а не команда автономных агентов: шаги здесь детерминированы,
«переговоры» между агентами задаче не нужны. `interrupt()` + чекпоинтер дают паузу
из коробки, в CrewAI это пришлось бы городить руками.

**Запасной режим.** Если LLM недоступна, `query_parser` откатывается на разбор регулярками
(числа, «двушка», город) — выдача хуже, но продукт работает.

## Интеграция: агент и MCP

Агент готов (`agent.py`), MCP-сервер пишет второй участник. Всё, что им нужно, лежит в `api.py`
и возвращает JSON-совместимые словари:

| Функция | Что делает |
|---|---|
| `search_listings(query, city, districts, rooms, price_max, …)` | поиск по условиям и стилю, с вердиктом по цене у каждого результата |
| `estimate_price(listing_id \| listing)` | диапазон p10/p50/p90, вердикт, надёжность |
| `get_comparables(listing_id)` | похожие объявления, на которых построен вердикт |
| `get_listing(listing_id)` | карточка объявления |

Две детали, важные для корректного вердикта:

- для объявлений из базы отдаются **out-of-fold** предсказания (модель их не видела),
  для новых — обученная на всех данных модель; поле `source` показывает, что именно;
- при малом числе аналогов `reliable=false`, и это надо показывать пользователю,
  а не прятать за уверенной цифрой.

## Трейсинг

Два независимых слоя, оба включаются переменными окружения.

**Arize Phoenix** (`tracing.py`) — локальный, без аккаунта и ключей.
Выбран вместо LangSmith потому, что поднимается локально и не требует аккаунта и ключей.
Обращения к ALEM идут через клиент OpenAI, который инструментируется автоматически:
в трейс попадают промпт, ответ, модель, токены и время. Свои шаги (`search_listings` как
retriever, `estimate_price` как tool) размечены вручную — иначе в дашборде видно только
«был вызов LLM», без контекста.

```bash
python -m phoenix.server.main serve     # дашборд: http://localhost:6006
TRACING=1 streamlit run app.py
```

Пример трейса одного запроса: `search_listings` (retriever, текст запроса в атрибутах)
→ 6 × `estimate_price` (tool, 18–43 мс) → `ChatCompletion` (llm, 4 с, 923 токена).

**LangSmith** — для трейсов агента. LangGraph логируется сам, а наши прямые вызовы ALEM идут
через голый клиент OpenAI, поэтому он оборачивается в `wrap_openai` (`tracing.wrap_llm_client`).
Включается ключом:

```bash
LANGSMITH_API_KEY=...        # ключ с smith.langchain.com
LANGSMITH_PROJECT=baga-ai
LANGSMITH_TRACING=true
```

Без ключа код работает как раньше, просто без отправки в LangSmith.

## Выбор моделей и параметров

| Задача | Что выбрали | Почему |
|---|---|---|
| Фото ↔ текст | `siglip2-base-patch16-224` | нужен общий вектор для картинок и текста; мультиязычная. Альтернатива `so400m-patch14-384` сильнее, но в 4–5 раз дольше (40–60 мин против 10 на Kaggle T4), а замеренное качество базовой версии нас устроило: precision@5 33–37% против 7.7% случайного выбора |
| Эмбеддинги описаний | ALEM `text-1024` | SigLIP плохо сравнивает текст с текстом; ALEM доступен по ключу курса, русский родной |
| LLM для объяснений | ALEM `alemllm` | единственная доступная нам модель без оплаты по токенам, отвечает по-русски. GPT/Claude потребовали бы платного ключа, а выигрыш для задачи «пересказать 5 аналогов» невелик: объяснение опирается на готовые числа, а не на рассуждение |
| Модель цены | CatBoost, `MultiQuantile` | категориальные признаки (район, улица, микрорайон) без ручного кодирования, устойчив к пропускам (у нас 41% координат, 36% ремонта), квантильная функция потерь из коробки |
| Не выбрали: DINOv3 | — | нет текстового энкодера, для текстового запроса непригодна. Оставлена как кандидат для признака «качество ремонта» по фото |

Параметры генерации: `temperature`, `max_tokens` подобраны экспериментом — см. `EVALS.md`,
раздел A/B по температуре. Судья в evals работает на `temperature=0` (нужна воспроизводимость).

## Данные

7 485 объявлений (после чистки 7 476), только помесячная аренда, Алматы и Каскелен.
72 963 фото → 71 679 файлов (дедуп по sha256). Один срез рынка, 21.09.2026.
Заполненность: адрес 100%, описание 98%, район 94% (колонка + разбор адреса),
координаты 41%, ремонт 36%, год постройки и тип дома ~0%.

## Ограничения

- Модель учится на ценах **объявлений**, а не сделок: отвечает «дороже похожих предложений».
- Один срез данных — динамики рынка и мониторинга дрейфа пока нет.
- Каскелен это 3.5% выборки, там ошибка заметно выше.
- Геозапросов («рядом со школой») нет: координаты только у 41%.
